MCP message writes (create, edit, withdraw) cannot create or preserve household-wide broadcasts. They require separate message-write consent, allowed recipient resources (people and/or displays), and the delegated member's live rights. An OAuth scope alone does not grant access to arbitrary people, displays, calendar sources, or school sources: grant rows and current server capabilities further constrain each call. The admin policy UI uses separate localized labels for calendar sources the client may read and displays it may access; these selections do not widen the client's OAuth consent.

## Output schema and timestamp conventions

Tool outputs are validated against their declared JSON schemas in `services/api/src/mcp/service.ts` and `services/api/src/mcp/household-tools.ts`. In particular, `household.messages.edit` returns exactly `{ "message": { "id": "<uuid>", "state": "scheduled|published", "revision": 2 } }`; message body and recipients are not echoed. The same ID/state/revision minimal projection is used for message lifecycle responses where specified. Other tools return named projections such as `people`, `events`, `items`, `assignment`, `option`, `plans`, or monitor status fields; consult each tool's declared schema for its exact limits and nullability. Some household schemas are permissive (for example passthrough fields); a scoped review identified this as a low-priority hardening follow-up. Schema validation is not a privacy boundary: SQL projections and server-side permission checks enforce data minimization.

All date-time values are JSON strings in ISO 8601 form with an explicit UTC offset (normally `Z`). Date-only values use `YYYY-MM-DD`; `localDate` denotes a household-local calendar date, not a UTC instant.
