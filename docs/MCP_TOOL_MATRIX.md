# MCP tool and domain-operation matrix

Local candidate `334e4df` contains 43 MCP tools through migration 071. Its new accountless person-profile tool passed 55 focused API and 21 web policy tests. The exact candidate then passed 925/925 isolated tests (web 312, contracts 7, core 3, API 603), API/web typechecks and an isolated Vite build. Evidence is under `.local/mcp-issue33/qa/final-43-334e4df/`. Synthetic schema-71 restore remains pending. The 42-tool predecessor `36487d52a5fc1e7b45a615cc813d85e1281cf656` passed 917/917 isolated tests and a synthetic schema-48→70 restore; those earlier results do not cover migration 071. Public source remains `8391041ca17ffea124870118b7312f0c50e3da5c` (schema 48), with no MCP endpoint. Public restore and named-client validation remain unverified.

The local candidate includes school source/week UI, monitor status and separately consented bounded result reads and personal review, grocery/dinner board writes, calendar reads and native-calendar writes, restricted message create/edit/withdraw, explicitly granted profile updates and display discovery/setup reads/appearance/layout updates, and protected PDF browser/download fallback. Message edit uses the existing message read/write scopes and no new migration. Native calendar writes use migration 062, `mcp:calendar:write`, the paired `mcp:calendar:read` scope, an explicitly granted native Samvev calendar resource, and approved person IDs; provider/ICS/HA sources remain read-only. Output timestamps are JSON strings: date-time fields use ISO 8601 with an explicit offset (typically UTC `Z`); date-only fields use `YYYY-MM-DD` household-local dates. Public deployment and real-client validation remain pending. Migration 063 adds separately scoped display appearance writes; migration 064 adds separately scoped personal monitor review; migration 066 adds separately scoped, inert monitor-draft creation; migration 067 adds display layout write consent and assignment revision tracking; migration 068 tracks MCP-owned display setup clones; migration 069 adds separate monitor draft update/delete consent; migration 070 adds separate monitor-name discovery consent; migration 071 adds separate accountless profile-creation consent, a household key fence and durable receipts. Output schemas describe response shape; authorization and privacy depend on server-side projections and checks. A scoped schema review noted low-priority hardening opportunity because some household output schemas are permissive; schemas are not a separate privacy boundary.

MCP message writes (create, edit, withdraw) cannot create or preserve household-wide broadcasts. They require separate message-write consent, allowed recipient resources (people and/or displays), and the delegated member's live rights. An OAuth scope alone does not grant access to arbitrary people, displays, calendar sources, or school sources: grant rows and current server capabilities further constrain each call. The admin policy UI uses separate localized labels for calendar sources the client may read and displays it may access; these selections do not widen the client's OAuth consent.

## Output schema and timestamp conventions

Tool outputs are validated against their declared JSON schemas in `services/api/src/mcp/service.ts` and `services/api/src/mcp/household-tools.ts`. In particular, `household.messages.edit` returns exactly `{ "message": { "id": "<uuid>", "state": "scheduled|published", "revision": 2 } }`; message body and recipients are not echoed. The same ID/state/revision minimal projection is used for message lifecycle responses where specified. Calendar write tools return exactly `{ "event": { "id": "<uuid>", "revision": 2 } }`. Other tools return named projections such as `people`, `events`, `items`, `assignment`, `option`, `plans`, or monitor status fields; consult each tool's declared schema for its exact limits and nullability. Some household schemas are permissive (for example passthrough fields); a scoped review identified this as a low-priority hardening follow-up. Schema validation is not a privacy boundary: SQL projections and server-side permission checks enforce data minimization.

All date-time values are JSON strings in ISO 8601 form with an explicit UTC offset (normally `Z`). Date-only values use `YYYY-MM-DD`; `localDate` denotes a household-local calendar date, not a UTC instant.
