# ADR 0025: Explicit AI reserve and UTC dispatch limit

Status: accepted for local review, 2026-10-28. Live provider compatibility remains an owner-controlled integration validation gate; synthetic transports do not establish live support.

AI settings retain the existing encrypted per-provider configurations and optimistic `expectedRevision` updates. A household administrator may explicitly select one distinct, already configured OpenAI API, Anthropic API or OpenAI-compatible reserve. The default is no reserve. ChatGPT subscription routes are excluded on both sides; fixed `openai` and `local` task policies never broaden. AI remains disabled by default.

A session can switch once, on its first request, before any successful provider turn, for an allowlisted transient server failure, recognized transport network failure, or proven provider rate limit. Authentication, permissions, billing/spend limits, model configuration, the local daily limit, cancellation, malformed content and unknown failures never qualify. A reserve starts from the original permitted task and tools, with no transplanted provider/tool history. Ordinary subsequent tool turns stay on that reserve. Fresh format repair and quality escalation that would switch back to the primary stop with a sanitized failure after reserve use; server output/evidence validation is never relaxed. This bounded limitation avoids introducing another routing cycle.

Queued executions pin selected settings revision, primary configuration revision and reserve provider/configuration revision. Every physical dispatch rechecks those pins, task revision/approval, a live matching task lease and, for queued work, live matching worker lease. Existing task instructions and schedules are not rewritten.

The optional positive `dailyDispatchLimit` is a UTC calendar-day request limit, not a currency budget. All physical requests share the same admission transaction, including setup, connection tests, tool turns, repairs and reserve calls. The household AI-settings row is locked `FOR UPDATE`; existing usage rows with `actual_dispatch IS DISTINCT FROM false` are counted, and inserting the existing durable `started` usage row reserves capacity. A confirmed pre-transport rejection changes that row to `actual_dispatch=false` and releases capacity. Unfinished/unknown dispatches remain counted after a process crash. Completion preserves the same reservation. Legacy unknown rows are counted conservatively. No guessed USD or provider-credit conversion is introduced.

Usage preserves each physical provider/model, configuration revision and reserve origin/reason. If the limit or local configuration prevents a reserve request, the primary remains a confirmed dispatch and the selected reserve is a separate `actual_dispatch=false` preflight row; selected provider identity never implies a transport call. Known Haiku 5.5 may receive forced tool choice, other/unknown Anthropic model IDs use automatic choice, and required tool results are checked server-side for every model. Settings expose only safe configuration flags/revisions and the current UTC count/remaining requests. Credentials remain encrypted and are never returned.

Migration 041 is additive, with null reserve and null limit defaults. Rollback: deploy the previous application while retaining additive columns; turn off the reserve/limit before downgrade if needed. Do not drop usage records or reverse existing migrations. No real household data or secrets are required.

Sources checked 2026-10-28: [Claude API errors](https://platform.claude.com/docs/en/api/errors), [Claude rate limits](https://platform.claude.com/docs/en/api/rate-limits), [API version migration](https://platform.claude.com/docs/en/api/migration-2026-10-21), [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs). In particular, an Anthropic 429 alone does not establish transient rate limiting, and preserved thinking blocks require an unchanged conversation prefix. External model/provider behavior may change; live validation is pending.
